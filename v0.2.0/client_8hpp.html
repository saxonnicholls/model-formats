Detailed Description

The Hugging Face Hub client: resolve a repository and revision, download its files into the shared cache, resumably, in parallel, verified, over ts-moveables' HTTP client and TLS.

Overview

resolve asks the public API (GET <endpoint>/api/models/<repo>/revision/<rev>?blobs=true) for the commit a revision names and every file in it with its size, git blob id and, for large files, its SHA-256. download fetches the files chosen by fnmatch patterns from <endpoint>/<repo>/resolve/<commit>/<path>, following the redirects to the CDN, in ranges of chunk_bytes with up to parallel files at once on one event loop, into blobs/<etag>.incomplete. An interrupted download resumes from the last whole range. A finished file is checked (SHA-256 for LFS files, the git blob id for the rest) before it is renamed into blobs/ and linked from snapshots/<commit>/, as huggingface_hub lays it out, so the two share one cache.

  • Auth: HF_TOKEN (or hub_options::token), sent as Authorization: Bearer to the endpoint's origin only (scheme, host and port), never to a redirect target elsewhere, never logged, never in an error (core's secret).
  • Offline: HF_HUB_OFFLINE=1 (or offline) answers from the cache alone: a revision resolved before, files present; anything else is offline.
  • Errors are respected: 401 / 403 (gated or private: a token is needed), 404 (no such repository, revision or file), 416 at a resumed end (complete), 429 and 5xx (http with the status), at most 10 redirects.
  • A cap: max_download_bytes refuses a download whose missing files sum to more, before any byte is fetched.
Relationships
See also
snicholls::http::client, snicholls::http::openssl_client_context (ts-moveables), formats::hub::cache, formats::hub::digest, formats::io::open_model_dir (opens the snapshot)
Implementations and variants

One event loop and one http::client (HTTP/1.1 over OpenSSL, certificates and host names verified); each file a chain of range requests in callbacks.

Guarantees and contracts

A failed download leaves the cache consistent: no blob is ever renamed into place unverified; .incomplete files stay for the next attempt. The client is not thread-safe: one call at a time.

Errors

bad_argument (an unsafe repository id, revision or path from the server), http (status, network, TLS), bad_json (an API answer of the wrong shape), checksum_mismatch, too_large (over the cap), offline, Files.

Examples
hub::hub_options opt = hub::hub_options::from_environment(); // HF_TOKEN, HF_HUB_OFFLINE, the cache
opt.endpoint = "http://127.0.0.1:" + std::to_string(port); // the real one is https://huggingface.co
opt.cache_dir = cache;
opt.offline = false;
hub::client hub(opt);
const auto info = hub.resolve("org/tiny-model", "main"); // the commit and every file, sized and hashed
const auto got = hub.download(*info); // verified, then linked into snapshots/<commit>
Performance

Not benchmarked; tiny-random-gpt2 (about 2.5 MB) downloads in about a second on a home connection.

Tests and demos

tests/hub/client_test.cpp (against ts-moveables' own http::server on localhost: listings, redirects, ranges, resume, a corrupted file, 404, 401, the cap, offline); tests/hub/client_network_test.cpp (label network, off by default: a small public repository from huggingface.co); demos/hub/client_demo.cpp.

Dependencies

ts-moveables (http/client.hpp, tls/openssl.hpp, event/loop.hpp, mmap/, fs/, process/config.hpp), OpenSSL 3.

Known issues and gotchas

Verification runs on the loop's thread, so a very large file pauses the other downloads while it is hashed. The ts-moveables client holds each response body in memory: chunk_bytes bounds it.

Status

Experimental.
